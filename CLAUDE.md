# laravel-worktree

A Laravel dev-tool package that provisions and tears down isolated git worktrees for local development. Each worktree gets its own application and test databases, a rewritten `.env`, and a local site served through a site driver (Herd, Valet, configured commands, a project's own class, or none). Five workflow Artisan commands: `worktree:setup`, `worktree:adopt` (provisions a worktree another tool made), `worktree:teardown`, `worktree:list` (worktrees with their URLs and databases), and `worktree:path` (which resolves a branch's directory for shell integrations), plus spatie's `worktree:install`, which publishes the config.

## Commands

```bash
composer test                  # lint + static analysis + type coverage + tests, the gate before every commit
composer lint                  # fix code style (Pint)
composer test:lint             # check code style without fixing
composer test:types            # PHPStan
composer test:type-coverage    # Pest type coverage (minimum 100%)
composer test:unit             # Pest

vendor/bin/pest tests/SomeTest.php          # one file
vendor/bin/pest --filter="test name here"   # one test
```

## Architecture

Everything runs from the **main repository**, not from inside the worktree. The commands create the worktree and then shell out into it. This avoids the chicken-and-egg problem where a freshly created worktree has no `vendor` yet.

```
src/
  WorktreeServiceProvider.php   Registers config, the five commands, spatie's install command (spatie/laravel-package-tools), and the adopt shim's publish tag
  Worktree.php                  Value object: derives name, host, path, and db names from a branch + config. Pure, no side effects.
  Commands/
    WorktreeCommand.php         Abstract base: process running (Laravel Process facade), git checks, main-repo guard, config access
    ProvisionCommand.php        Abstract base of setup and adopt: everything after a worktree is named (guards, record, site, .env, dependencies, databases, steps, summary)
    SetupCommand.php            worktree:setup (names the worktree from the branch, creates or resumes it)
    AdoptCommand.php            worktree:adopt (provisions a worktree another tool made, named by --name, the tool, or a path hash)
    TeardownCommand.php         worktree:teardown
    ListCommand.php             worktree:list (branch, path, URL, database names per worktree, incl. sibling SQLite files)
    PathCommand.php             worktree:path (an adopted name's recorded directory, a branch's checkout, else its derived directory)
  Contracts/
    SiteDriver.php              The public site driver contract (available, url, serve, isServed, unserve, timeoutHint). Never grows: later capabilities are optional interfaces.
    SiteRunner.php              What a driver hands its commands to (run, warn)
  Drivers/
    Driver.php                  Abstract base with the defaults most drivers share, plus executable() for binary lookup and attempt() (run, warn on failure)
    HerdDriver.php              herd link / links --json (table fallback) / secure / unsecure / unlink, every one by name
    ValetDriver.php             valet link / secure / links / unsecure / unlink for Valet, valet-linux and valet-windows, by name
    CommandDriver.php           The serve, secure, check, unsecure, unserve commands a project configures
    NoneDriver.php              Serves nothing
  Support/
    SiteSettings.php            Resolves the site driver (a name or a driver class), secure flag, and timeout from config, including the legacy `herd` key. Pure (availability through a callback).
    SiteList.php                Reads a server's site list for one name: hasCell() for tables, mentions() for any output. Pure.
    ProcessSiteRunner.php       The SiteRunner: env scrub, site.timeout, timeouts and start failures turned into warnings
    EnvFile.php                 String editor for .env (set key, remap host). Pure.
    PhpunitConfig.php           DOMDocument editor for phpunit.xml <env> entries. Ignores commented defaults.
    DatabaseManager.php         Classifies a driver server (mysql/mariadb/pgsql) vs file (sqlite); create/drop via raw PDO for server drivers, connecting without selecting a db.
    DatabaseCloner.php          Copies a database into a new one for --clone: server-side table copy (MySQL/MariaDB), template copy (Postgres), VACUUM INTO (SQLite).
    WorktreeList.php            Parses `git worktree list --porcelain`. Pure.
    Directory.php               Recursive delete that never follows a symlink or Windows junction, plus isEmpty(), isLink() and removeLink(). Pure.
    Registry.php                The worktrees setup recorded (name, driver, secure, url, databases with their DSN, sibling files), as JSON in the git common dir. Read, put (merging), forget, save by rename.
    FileLock.php                An flock on a file of its own, polled through Sleep up to a limit.
  Enums/
    HerdMode.php                secure | link | none: the legacy `herd` values, read by SiteSettings; kept because old published configs import it
    MigrateMode.php             fresh | migrate | none
    FinishMode.php              pr | merge | abandon (teardown)
  Exceptions/WorktreeException.php   Named factory methods
config/worktree.php             The full configuration surface
resources/stubs/worktree-adopt.php   The shim a tool's worktree setup script runs (published with --tag=worktree-adopt, committed in the app)
```

## Key design decisions

- **Pure support classes.** `Worktree`, `EnvFile`, `PhpunitConfig`, `DatabaseManager` (statement/dsn builders), `WorktreeList`, `SiteSettings`, `SiteList`, and `Registry` (apart from its file read and save) hold the real logic and have no side effects, so they're unit-tested directly. The commands are thin orchestration over them.
- **Child processes get the main app's .env keys unset** (`WorktreeCommand::sourceEnvironment()`). This is the single most important thing in the package. Laravel putenv()s the app's own .env and Symfony passes the parent environment on to children, while phpdotenv refuses to overwrite a variable that is already set. So `php artisan migrate:fresh` run inside the worktree used to read the *main* app's `DB_DATABASE` and drop the *main* database while reporting success. Passing each key as `false` unsets it for the child, which then loads its own .env normally; anything not in the .env (PATH and friends) is still inherited. Any new child process must go through `process()`/`attempt()`/`capture()` (or the site runner, `WorktreeCommand::siteRunner()`, for driver commands) so it keeps this. Two exemptions start no artisan or env-reading child: the provider's browser opener for the install command, and `Driver::executable()` (also how setup's Lerd check finds Lerd), whose Symfony `ExecutableFinder` falls back to `command -v` on Linux and macOS. The adopt shim (`resources/stubs/worktree-adopt.php`) starts the main checkout's artisan, but from a plain PHP script that loaded no `.env`, so there is nothing to scrub; adopt's own children go through the runners like setup's.
- **Drivers split into server and file** (`DatabaseManager::isServer()` / `isFile()`), because the isolation problem differs. A server database (mysql/mariadb/pgsql) is shared, so each worktree needs its own named database created and dropped. A file database (sqlite) lives inside the worktree and is already isolated: nothing is named or dropped, and an absolute `DB_DATABASE` pointing back at the source is redirected (`Worktree::mapPath()`). The file itself *is* created, because Laravel gitignores it (`database/.gitignore` holds `*.sqlite*`) so a fresh worktree never receives one from git and `migrate` would fail. This is what makes a stock Laravel app work untouched.
- **A SQLite file outside the repository is handled like a server** (`WorktreeCommand::databaseFile()`/`siblingDatabaseFile()`/`isOutsideFile()`/`resolveFile()`). "Outside" is decided on the path resolved against the main repository (Laravel resolves a relative SQLite path against the app directory), so `../blog.sqlite` counts too: classified on the raw string it looked relative, so inside, and run from a sibling worktree it landed on the main file. It used to be left shared with a warning, and the worktree's `migrate:fresh` then wiped the main file (with `--clone` the user asked for a copy and got that wipe). Now the worktree gets a sibling file in the same directory, named by the entry's `name` template with the source's extension, written to the worktree `.env` (`ProvisionCommand::applyConnectionEnv()`, which also handles a `.env` without the key when the config resolves outside the repo), cloned into on `--clone`, shown by setup's summary and `worktree:list`, and deleted (with `-wal`/`-shm`/`-journal`) by teardown. `guardSourceFile()`/`isSameFile()` refuse a template that names the main file itself, comparing canonical paths without case (Windows and macOS filesystems ignore it), both before the worktree is created and right before a clone deletes the target. `guardDuplicateDatabases()` (through `namedDatabase()`) also refuses two SQLite entries whose worktree files would be the same file.
- **Setup records what it made, and teardown and list read the record** (`Support\Registry`, `WorktreeCommand::registry()`/`updateRegistry()`, `ProvisionCommand::recordWorktree()`, `TeardownCommand::recordedSiteSettings()`/`recordedDrops()`). Deriving names from the configuration again broke as soon as the configuration moved: a changed name template orphaned the real databases (and dropped whatever the new template named), a switched driver unserved through a server that never served the worktree, and a detached HEAD had no branch to derive from, so its databases stayed. The registry lives at `<git-common-dir>/laravel-worktree/registry.json` (per clone, never committed, found with `git rev-parse --path-format=absolute --git-common-dir`); each entry is keyed by the worktree's canonical path and holds the name, branch (git's, null when detached), tool (`setup`, `adopt`, `--tool`, or the tool whose variables named it), resolved driver and secure flag, host, URL, every server database (application and test) with its connection's resolved name and `DatabaseManager::dsn()` (which holds no password), and every sibling SQLite file with its main file. Setup writes it right after `git worktree add`, under the same lock, so a setup that fails later still leaves an entry; the databases are the ones it is about to create (a drop of one never created is harmless), and test databases are recorded per PHPUnit file present, mirroring `prepareTestDatabasesFor()`. A resumed setup's `put()` unions databases and files with the earlier entry, so a `--no-database` rerun never forgets them; and resuming a worktree an earlier release made (no entry yet) records the configured databases even under `--no-database`, since that release made them and teardown trusts the entry (`createWorktree()` returns whether it resumed). `normalize()` keeps keys it doesn't know, so a field a later release adds survives this release's next save. Teardown unserves with the recorded driver, secure flag and name (a recorded driver that no longer resolves, such as a deleted class or one the container can't build, serves nothing and teardown warns to stop the site by hand: the configured driver never served the worktree, and a same-named site there may be someone else's), drops only a recorded database whose connection's current `dsn()` still equals the recorded one (otherwise a warning: the name may belong to something else on the new server), refuses a recorded file that is now a main SQLite file (`isSourceFile()`), keeps the main-database guard, the derivative sweep and the confirmation, and forgets the entry last. A worktree with no entry (made by an earlier release) keeps the derived path (`derivedDrops()`). A registry that doesn't decode, or carries a newer `version`, throws `unreadableRegistry()`: read paths warn and fall back, writes warn and leave the file as it is, so a corrupt file is never overwritten as empty. A failed save (including a `JsonException` for a name that isn't UTF-8) warns and the command carries on: the registry is bookkeeping. The rename is retried with backoff because Windows refuses to rename over a file another process has open, which an unlocked reader does for a moment. `registryDirectory()` resolves a relative answer (a git too old for `--path-format`) against the repository, not the process's working directory.
- **Commands on one repository take turns through a lock** (`WorktreeCommand::locked()`, `Support\FileLock`). Agents run setups in parallel, and two of them reading and rewriting the registry together would lose an entry; two `git worktree add`s and two servers linking at once can trip over each other too. `locked()` holds an `flock` on `<git-common-dir>/laravel-worktree/lock` (a file of its own: Windows locks are mandatory, so locking `registry.json` would block its readers) around setup's resume check, `git worktree add` and registry write together, around each driver's `serve()` and `unserve()`, and around every registry write. It is re-entrant through `$lockDepth`, so `updateRegistry()` inside a locked step doesn't wait on itself. No PID check: the OS drops an `flock` when its process exits. A waiting command says so once, polls four times a second through `Sleep` (faked in tests, which then run the wait instantly), and throws `lockTimeout()` after `lockSeconds()` (600). With `site.timeout` at 0 a driver command stuck on a dialog holds the lock until it answers, and the others time out. Readers (list, teardown's first read) don't lock; the save is a temp file renamed into place.
- **Databases are provisioned per connection from a config list** (`WorktreeCommand::databaseConnections()`, `ProvisionCommand::createConnectionDatabase()`/`prepareTestDatabases()`, `TeardownCommand::dropDatabases()`). Each entry names the Laravel connection (`null` = the app default), the `.env` key holding its database name, a name template, and an optional `test` block. The env key cannot be inferred: Laravel resolves `env()` at boot, so the connection config it exposes holds the value, not the variable, and there is no reverse map, which is why the user declares it. Setup loops the list to create each database (or sqlite file) and rewrite each key; teardown loops it to drop each on its own connection. `ProvisionCommand::guardDuplicateDatabases()` throws before any worktree is made if two entries resolve to the same name on one server (same `DatabaseManager::dsn()`).
- **The phpunit rewrite follows each connection's test connection, not the app's** (`ProvisionCommand::prepareTestDatabases()`, `WorktreeCommand::testConnectionFor()`). A stock Laravel `phpunit.xml` pins the suite to in-memory sqlite; rewriting the key there would point sqlite at a file named after a database. Only a server test connection gets a test database and a rewrite, and an entry with no `test` block is skipped. Each test name is written into the one phpunit file, then the file is marked skip-worktree once.
- **The default connection's test database follows the phpunit connection, not the app default** (`WorktreeCommand::testConnectionFor()`/`phpunitConnection()`). An app developing on sqlite with a mysql test suite needs the test database on mysql; a `null` connection entry resolves its test connection from the worktree's phpunit `DB_CONNECTION`, while a named connection keeps its name in tests too. Teardown resolves every entry's test connection from the phpunit file *before* removing the worktree, because the file dies with it. The main-database guard (`WorktreeCommand::isSourceDatabase()`/`sourceDatabaseNames()`, shared by setup and teardown) checks a name against every entry's configured database and every entry's env keys in the source env file, lowercased: a worktree name on one connection can still land on another connection's main database when they share a server, and MySQL on Windows and macOS ignores case, so `Blog` is `blog`. `DatabaseManager::driver()` deliberately defaults to `''` so an unknown connection name (empty config array) classifies as unsupported instead of silently becoming mysql on 127.0.0.1.
- **Published configs are re-merged nested** (`WorktreeServiceProvider::packageRegistered()` → `mergeConfig()`). Laravel's `mergeConfigFrom` (what spatie's `hasConfigFile()` calls) is a shallow `array_merge`, so a user's published `database` block would replace ours wholesale and silently lose a key we add later, such as a new connection. After that shallow pass, `mergeConfig()` deep-merges maps but *replaces* lists: a nested option group fills in from the defaults, while a list the user set (`steps`, `connections`) stays theirs rather than being index-merged (which would leak default steps back in or scramble connection entries). A *collection* (`$collections`, today only `dependencies`) is a map whose keys are the user's entries, so `mergeCollection()` keeps only the published keys and deep-merges each into its default entry: a deleted `node_modules` stays deleted (the plain deep merge used to refill it and run `npm ci` in a project with no lockfile), while a kept entry still picks up new options. Guarded by `configurationIsCached()` so a cached config is left untouched.
- **Every command refuses to run from a linked worktree** (`WorktreeCommand::isMainRepository()`, compares `git rev-parse --path-format=absolute --git-dir --git-common-dir`; they diverge only inside a linked worktree). From inside a worktree, setup derives names from the worktree's own directory and teardown auto-selects the main repo as the only "other" worktree to destroy. A base path merely nested in the main working tree (monorepo app) passes, and an empty git answer (old git without `--path-format`) fails open rather than blocking.
- **Site drivers serve the worktree; Herd is one of them** (`Contracts\SiteDriver`, `Drivers\`, `WorktreeCommand::siteSettings()`/`siteDriver()`/`siteRunner()`). Setup serves through the resolved driver before it writes `.env` (which is copied fresh every run, so whatever a server writes there while linking is overwritten), writes `APP_URL` from `url()` or `http://{host}` when the driver serves nothing (an empty `env.app_url_key` skips that), and shows the URL row only when `serve()` returned true and `url()` isn't null (`APP_URL` keeps the address either way, so serving the site by hand later needs no `.env` change); list shows `url()` or `-`; teardown calls `unserve()` with the directory name, since a detached worktree has no `Worktree`. The drivers are `herd`, `valet`, `command`, `none`, and any class implementing the contract named in `site.driver`, built with `$this->laravel->make()` (`SiteSettings::isDriverClass()`). A new built-in driver is added in three places: `SiteSettings::drivers()`, `SiteSettings::installed()` when `auto` should pick it, and the match in `WorktreeCommand::siteDriver()`. Drivers never start processes: they hand argv lists to the runner passed into each method, which keeps the env scrub and stderr routing under `--print-path`; an arch test pins that `Drivers\` uses neither the `Process` facade, Symfony's `Process`, nor PHP's process functions. Every method is best effort and reports through `SiteRunner::warn()`. The contract is public (a project can write its own driver), so it never gains a method after release; a later capability arrives as an optional interface checked with `instanceof`. The README documents implementing the interface only: `Drivers\Driver` is the built-in drivers' shared base and stays free to change, so never document it as something to extend.
- **The driver is resolved at read time, with the old `herd` key as an alias** (`Support\SiteSettings::resolve()`). The config merge fills every new key from the defaults, so `site.driver` ships as `env('WORKTREE_DRIVER')` with no default and the shipped `herd` key as `env('WORKTREE_HERD')` with none either: when `site.driver` is empty the legacy value decides (`secure`, `link`, `none` through `HerdMode`), and with both empty `auto` picks Herd when its binary is found, else Valet, else `none`. An unknown `site.driver` throws `unknownSiteDriver()`; an unknown legacy value (including the booleans `env()` makes of `true`/`false`) keeps meaning Herd over HTTPS, as it always did, with a warning, so no published config breaks. A driver asked for by name or by the legacy key but not available resolves to `none` in every command, and setup alone warns, saying what to fix for that driver (`auto` falls back quietly). The `command` driver chosen with no `serve` command throws `commandDriverUnconfigured()`, a mistake in the config like an unknown name. `site.secure` is read with `FILTER_VALIDATE_BOOL` after `null`/`''` count as unset, and defaults to on for Herd unless the legacy value said `link`, and off for every other driver: Valet's `secure` asks for sudo and trusts a certificate, which a user who configured nothing never asked for. A config cached under an older release has no `site` block (the merge is skipped when config is cached), so every `site.*` read has a code default. Commands resolve it fresh in each `handle()` (the console reuses command instances), and teardown resolves it before finishing, so a bad driver stops it before a merge or push.
- **The `command` driver runs argv templates from config** (`CommandDriver`, `site.drivers.command`). Each of `serve`, `secure`, `check`, `unsecure` and `unserve` is a list of arguments, or a string split on spaces before its tokens are expanded (so a path with a space stays one argument). `serve`/`secure` run in the worktree with every `Worktree::tokens()` token plus `{path}`; `check`/`unsecure`/`unserve` run from the main repository with only `{name}`, `{path}`, `{host}` (`{name}.{tld}`) and `{tld}`, since teardown may have no `Worktree`. The check passes when its output mentions the name between the boundaries `SiteList::mentions()` uses (`EnvFile::remapHost()`'s, with `_` added and `.` allowed after, so `name.test` and URLs match but `blog-feature-login` never counts as `blog-feature`). `available()` is the serve command's program being found.
- **Setup warns when Lerd serves the repository** (`ProvisionCommand::warnAboutLerd()`, `site.lerd.binary`). Lerd's watcher provisions every new git worktree of a site it serves (its `.env`, dependencies, vhost), so it and setup would provision the same worktree at once. A `.lerd.yaml` in the main repository says so without a process; otherwise `lerd sites` is read through a runner of its own (a Lerd timeout must not skip the driver's commands) for the repository's name or host as a cell. The path is never compared: Lerd prints it shortened with `~`. Lerd isn't a driver yet, so its binary lives outside `site.drivers`; null skips the check.
- **Herd sites are always linked, then secured** (`HerdDriver::serve()`). Herd only serves parked and linked directories; a worktree in a nested path (`path => '.worktrees'`) is neither, and `herd secure` alone mints a certificate for a site that never answers until it is linked. Linking a parked worktree is harmless. Teardown unsecures (secure mode) and always unlinks.
- **Every Herd and Valet command names the site, and teardown's run from the main repository** (`HerdDriver`, `ValetDriver`). Herd's `unsecure` and `unlink` without a name find the site from their working directory, which from the main repository is the main site; valet-linux's `unlink` without a name removes the link named after the directory, not the one linked from it. With the name given, teardown no longer needs the worktree directory, so a site whose directory is already gone is still unlinked (it used to be skipped and left linked). `link` alone runs in the worktree, because both link their working directory.
- **A resumed setup does not relink a Herd site it already serves** (`HerdDriver::servesAlready()`). `herd link` rewrites `APP_URL` in the cwd's `.env` and runs `php artisan boost:update` when `vendor/laravel/boost` exists, so it is skipped when `herd links` already lists the site; only a worktree with a `.env` or `vendor` (one an earlier run provisioned) is checked, so a fresh setup pays no extra call. `secure` still runs, since an earlier run may have linked and then failed to secure.
- **Driver commands run with a time limit, 60 seconds by default** (`ProcessSiteRunner`, `site.timeout`). Herd's CLI (`herd.phar`, `Valet\Herd::makeAppRequest()`) asks the Herd app over HTTP with curl and no timeout, so while the app is stuck on a dialog, or on Windows an elevation prompt, `herd link` waits forever, and setup used to hang with it. A timed-out command is killed (Symfony kills the process tree), warned about with the driver's `timeoutHint()`, and counts as failed; the runner then skips that driver's remaining commands for the run, naming each so the user can run it by hand, since teardown would otherwise wait out the limit once per command. Setup and teardown carry on. The runner catches Laravel's `ProcessTimedOutException` before Symfony's `RuntimeException` (its parent), which covers a missing working directory and a binary that can't start. The same CLI ignores a failed app request, so `herd link` can exit 0 having linked nothing, and it links in the background; `HerdDriver::serve()` reads `herd links --json` up to five times a second apart (`Sleep`, faked in tests), matching `site` exactly rather than by substring (`blog-feature` used to count as linked when only `blog-feature-login` was), and warns, without securing, when the site never shows (it stays quiet when the list itself can't be read). A Herd without `links --json` fails it or prints a table, so the driver falls back to an exact cell match in `herd links` (`SiteList::hasCell()`) and keeps the table for the rest of the run. Valet links synchronously and exits non-zero when it can't, so its list isn't read after linking (each extra Valet command may ask for a password).
- **Setup resumes a same-branch worktree instead of throwing** (`SetupCommand::isExistingWorktree()`). A failed step used to strand a half-provisioned worktree that only teardown could clear. Every provisioning step is idempotent (create-if-missing databases, `migrate:fresh`, `npm ci`), so re-running is safe. A directory registered to a *different* branch still throws `worktreeExists`.
- **Adopt provisions a worktree another tool made through setup's own path** (`AdoptCommand`, `ProvisionCommand::provision()`). Agent apps and editors make worktrees that copy `.env` and so point at the main database. Setup and adopt share everything after naming in the abstract `ProvisionCommand`, not by adopt extending setup: larastan checks every `option()` literal in a class against each registered subclass's signature, so setup's `--base`, `--print-path` and `branch` would fail for adopt. Each passes `provision()` a closure that makes the worktree (or not) and says whether it resumed, run under the lock after `guardNameTaken()`. Adopt refuses the main checkout (the base path or git's first entry: adopting it would copy `.env` onto itself), a path `git worktree list` doesn't show, and a worktree setup made (recorded with tool `setup`, or unrecorded, on a branch, at exactly the path setup gives that branch's worktree: `samePath()` against `worktreeFor()->path()`), pointing at `worktree:setup <branch>` so setup's names stay setup's. `Worktree::withPath()` fixes the directory the way `withName()` fixes the name, each carrying the other. The name is the host template with a label in `{branch}`, so the repository prefix stays in every host and database name (and the `wt_` prefix the test databases rely on): `--name`, then a tool's variable (`$tools`: Conductor's `CONDUCTOR_WORKSPACE_NAME`, trusted only while `CONDUCTOR_WORKSPACE_PATH` is this worktree, so an adopt run by hand from that terminal doesn't borrow it; read with `getenv()`, not `env()`), then the first 8 hex of `md5` of the canonical path, never the branch (many tools start detached). A recorded worktree keeps its recorded name, and a different `--name` only warns. The registry records git's branch (null when detached), not the label, and the tool (`--tool`, the variable's tool, the recorded tool, else `adopt`). Adopt never reports a resume, so `--no-database` records no databases.
- **No two worktrees share a name** (`ProvisionCommand::guardNameTaken()`/`sharesDatabases()`, setup and adopt, under the lock). An adopted worktree sits wherever its tool put it, so two under one name would share a site and every database named after it, and the second one's `migrate:fresh` or clone would wipe the first one's data. Names are compared by slug, since databases are named from it (`blog-feature_login` and `blog-feature-login` both give `blog_feature_login`): against every other listed worktree's recorded name, or its directory name when unrecorded (setup names directories after their worktree), and against the repository's own name, which is the main site's (a host template without `{repo}` could otherwise link a worktree over it).
- **Links a tool left in its worktree are removed before anything is written** (`ProvisionCommand::removeSharedLinks()`, `Directory::isLink()`/`removeLink()`). Conductor's docs suggest linking `.env` to the main one, and a write through a link lands in the main app: `.env` rewritten (by `prepareEnvironment()`, whose `copy()` of a file onto itself fails silently, and by `herd link`'s `APP_URL` rewrite), an in-repo SQLite file migrated fresh, `vendor` or `node_modules` installed over. Only what the run will write is checked: `.env`, each dependency path whose manifest is present (unless `--no-install`), and each in-repo SQLite file and PHPUnit file (unless databases are off). Each that is shared (`isShared()`: a link or Windows junction whose target resolves outside the worktree, or a regular file with more than one hard link, which Laravel's `File::link()` makes for files on Windows) is removed, never its target, with a warning, before the driver serves; a PHPUnit file keeps the linked contents, since it is patched in place. A link inside the worktree (a committed relative symlink) stays, or the worktree would be dirty. One that can't be removed throws `linkedFile()`. `env.copy` targets are skipped: an existing one is never written. `Directory::isLink()` counts a path that is neither link, directory nor file as a junction on Windows only; elsewhere that is a pipe or socket.
- **Teardown and path find an adopted worktree by its recorded name** (`TeardownCommand::matchWorktree()`, `PathCommand::recordedPath()`). A name matching more than one worktree (an adopted name equal to another worktree's branch or directory) throws `ambiguousWorktree()` rather than finishing the first, since teardown deletes the branch. Teardown names a detached worktree by its directory (`describe()`). A worktree path matches however it is spelled (`samePath()`). A worktree with no record is unserved by its directory name, and its databases derived from the configuration, only when that is the name setup gives its branch (`WorktreeCommand::setupName()`, which `worktree:list` also uses to show such a worktree with no URL or databases; names are compared so a gone directory still matches): any other came from another tool, so this package never served it or made its databases, and some tools check out every worktree as `<id>/<repository>`, whose directory name is the main site's. Teardown says so in a warning and leaves its site and databases alone. `worktree:path` prints a recorded name's path, then git's checkout of the branch (`registeredPath()`), then the derived path, and routes warnings to stderr because shells capture its stdout.
- **The adopt shim is a PHP file the app commits** (`resources/stubs/worktree-adopt.php`, `vendor:publish --tag=worktree-adopt` to the project root). A tool's setup script runs inside the new worktree, which has no `vendor`, and PHP runs wherever artisan does, unlike `sh` on Windows. It finds the worktree with `git rev-parse --show-toplevel` (a tool may run it from a subdirectory, and an MSYS `$PWD` wouldn't match git's paths) and the main checkout as the first `git worktree list --porcelain` entry (the parent of `--git-common-dir` is wrong for a repository with a separate git directory), then runs `PHP_BINARY -d display_errors=stderr <main>/artisan worktree:adopt <top> ...args` from the main checkout through `proc_open` with an array (no shell quoting), passing stdio and the exit code through.
- **Database names are capped at 63 chars** (`Worktree::database()` → `fitDatabase()`). MySQL rejects identifiers over 64; Postgres silently truncates at 63, after which the full name written into phpunit.xml could never connect. Each name template is fit on its own (application and test names are independent, not app-plus-suffix), and an over-long name is cut and suffixed with `_`+6 chars of md5 so two truncated branches can't collide on one database.
- **The worktree name is capped so the host fits a TLS certificate** (`Worktree::name()` → `fitName()`, sharing `fit()` with `fitDatabase()`). A certificate's common name holds 64 characters and a DNS label 63, so `herd secure` failed for a long repo plus a long branch. The name is cut to `63 - strlen('.'.tld)` with `-`+6 chars of md5. Because the directory, host, `{slug}`, and database names all derive from `name()`, they stay consistent. A worktree made before the cap is named after the uncapped name on disk, so every command that names a worktree after its branch builds its `Worktree` through `WorktreeCommand::worktreeFor()` (adopt names its own from a label and a fixed path): when the cap changed the name and the branch's registered worktree (or the path teardown and list already have) sits in a directory named after `uncappedName()`, it uses `withName()` to keep that name. Path, setup (which then resumes instead of hitting git's "already checked out"), list, and teardown (which then drops the databases that really exist) all go through it. The git lookup only runs when the cap changed the name. Pinned by a test that makes a long-named worktree with raw `git worktree add`, as an older release would have.
- **`env.copy` copies only gitignored files** (`ProvisionCommand::copyExtraEnvironmentFiles()`, checked via `git check-ignore`). A tracked file arrives through git already; an untracked-but-not-ignored copy would dirty the worktree, block merge teardowns, and ride into a `--pr` commit. Copies get the host remap and the configured `env.replace` rewrites and nothing else; test-database isolation stays phpunit.xml's job because phpunit `<env>` values outrank `.env.testing` (phpdotenv refuses to overwrite set variables).
- **Arbitrary env values are isolated through a config-driven `env.replace` map** (`ProvisionCommand::applyEnvReplacements()`), not a hardcoded handler per key. Each entry is `KEY => template`; the template is expanded with the worktree tokens plus a per-key `{value}` holding the key's current value, so a project appends its worktree slug to a Redis or cache prefix (`{value}{slug}_`) without the package ever knowing that key exists. `{value}` is the value *in the file*: a stock Laravel `.env` leaves `REDIS_PREFIX` and `CACHE_PREFIX` out (config builds them from `APP_NAME`), so for those it is empty, which is why the documented example writes whole prefixes (`{slug}-database-`, `{slug}-cache-`). Applied to the copied `.env` and to every `env.copy` file, after the host remap. `DB_DATABASE`, `APP_URL`, and the host remap stay separate and are *not* folded in: the first has driver-dependent logic a template cannot express, and letting an editable map silently drop the other two would be a footgun. It is idempotent because `prepareEnvironment()` re-copies `.env` from source every run and the extra files are skip-if-exists, so `{value}` always reads the pristine source value and a resumed setup never double-appends.
- **All configurable templates share one token vocabulary** (`Worktree::expand()`/`tokens()`), so `{slug}` means the same thing in a `database.connections` name and in `env.replace`. The host template is the deliberate exception: it feeds `name()`, which `{name}`/`{slug}`/`{host}` all derive from, so `name()` expands only the pre-name `{repo}`/`{branch}`, and `tokens()` omits any database-derived token to keep `expand()` from recursing.
- **Dependency directories are provisioned from a config list that copies instead of installs when it is safe** (`ProvisionCommand::provisionDependencies()`/`copyDependency()`). Each `dependencies` entry names a directory, its manifest, its lock file, and an install command. With `copy` on, the directory is copied from the main repository (`WorktreeCommand::copyDirectory()`: robocopy on Windows, `cp -a` elsewhere) and the install is skipped, but only when the worktree's lock file is byte-for-byte the main repo's (`locksMatch()`), so a branch that changed its dependencies gets a real install rather than a stale copy. An entry whose manifest is missing from the worktree is skipped entirely, which is why `npm ci` lives in `dependencies` and not `steps`: a project with no `package.json` then runs no npm at all. Robocopy is passed backslash paths because it rejects the forward slashes `Worktree` normalizes to, and its success codes (< 8) are read directly since a normal copy exits 1, not 0. Copying skips the downloading, unpacking and install scripts of an install, so it takes a fraction of the time.
- **Teardown also drops parallel-test derivatives** (`DatabaseManager::parallelDerivatives()`, folded into `TeardownCommand::dropDatabases()`). Test runs create `{name}_test_{token}` databases next to the worktree's own (paratest worker indexes, `mozex/laravel-test-lanes` lanes) outside the worktree flow, so teardown discovers them by LIKE pattern and drops them with the databases they derive from. Discovery runs *after* the source-database guard on purpose: it opens a connection, and the guard must refuse before any connection is attempted (pinned by the "honors the configured env file" test); each discovered name is then checked against the same guard individually and skipped with a warning on a match. Derivatives are dropped `WITH (FORCE)` like every other worktree database and deliberately without checking their advisory locks: teardown destroys the whole worktree (it force-drops the base test database even while connections hold it, test-pinned), and skipping an in-use lane would leave behind exactly the orphan this feature removes.
- **Cloning copies the main database into the worktree's instead of starting empty** (`ProvisionCommand::cloneServerDatabase()`/`cloneDatabaseFile()`, `DatabaseCloner`). Opt-in (`database.clone.enabled`, `--clone`, `--no-clone` wins), and its own switch rather than a `MigrateMode` case because cloning with `migrate => none` is valid. Every connection entry is cloned, with no per-entry opt-out on purpose: Laravel records every migration, including those pinned to a second connection, in the default connection's `migrations` table, so cloning some connections and not others leaves that table out of step with the empty ones (their pinned migrations read as already run, or a fresh default re-runs them against a cloned connection). A huge table goes in `structure_only` instead. Each driver gets its cheapest copy:
  - MySQL/MariaDB copy server side over PDO: `SHOW CREATE TABLE` read on a source-db connection and replayed on a target-db connection (so references come back unqualified and resolve in the target), then every row in one transaction with `INSERT ... SELECT` across the two databases at READ COMMITTED (under the default REPEATABLE READ, `INSERT ... SELECT` takes shared locks on every source row it reads and the one transaction would hold them until the end, stalling the main app's writes or failing the clone on a lock wait timeout; pinned by a test holding an open `UPDATE` on the source). A server binlogging in `STATEMENT` format rejects READ COMMITTED writes with error 1665, so the copy session first tries `SET SESSION sql_log_bin = 0` (a dev copy has no business in the binlog; needs a privilege, so failure is ignored), and on 1665 `insertRows()` reruns the copy at REPEATABLE READ, locking but working. A server with binary logging off never raises 1665, so that path is tested with a cloner subclass that stages the refusal. Then routines, views (in passes, for views on views), and triggers last so they never fire on copied rows. Session `FOREIGN_KEY_CHECKS=0` and `sql_mode='NO_AUTO_VALUE_ON_ZERO'` mirror mysqldump (a row with id 0 keeps it). Generated columns are skipped by a non-empty `generation_expression`, not by `EXTRA`, because MySQL flags a plain `DEFAULT CURRENT_TIMESTAMP` column `DEFAULT_GENERATED`. DEFINER clauses are stripped (`withoutDefiner()`) so a local user can recreate them. No client binaries are needed, which matters on Windows and with Docker-hosted servers.
  - Postgres uses `CREATE DATABASE ... TEMPLATE`. Postgres refuses it (SQLSTATE 55006, after waiting about five seconds) while any other session is connected to the source, which a queue worker or a database GUI is enough for, so `createFromTemplate()` returns false on exactly that and setup falls back to `pg_dump --format=custom` into a temp file plus `pg_restore`, run through `process()` with `PGPASSWORD` in the env (never on the command line). It never terminates the main database's sessions. Missing tools throw `cloneSourceBusy()` naming both fixes.
  - SQLite uses `VACUUM INTO`, which captures rows still in a WAL file (a plain file copy would not). The source is not opened read-only on purpose: the `PDO::SQLITE_*` open-flag constants are deprecated in PHP 8.5 and `Pdo\Sqlite` does not exist before 8.4.
  - `structure_only` tables (wildcards via `Str::is`, matched with and without the connection's table `prefix`) keep their schema and lose their rows: skipped in the MySQL copy, truncated in one statement after a Postgres copy, deleted after a SQLite copy. The queue tables are the point: a worktree worker would otherwise re-run the main app's pending jobs. Postgres refuses to `TRUNCATE` a table a kept table has a foreign key into (SQLSTATE 0A000), so `deleteUnenforced()` deletes the rows under `session_replication_role = replica`, leaving dangling keys exactly as the MySQL copy (FK checks off) and SQLite (FK enforcement off by default) do. That needs a superuser or, from PG15, a granted SET; without one `structureOnlyReferenced()` names both ways out.
  - A cloned default connection turns `fresh` into `migrate` (or `migrate:fresh` would wipe it) and skips `database.seed` (only `--seed` seeds a clone). This keys on the default connection's entry (`clonedDefaultConnection()`), not on any clone, since migrate and `--seed` act on the default alone and it may have had no main database to copy. Test databases are never cloned. A resumed setup drops the target and clones again, mirroring `migrate:fresh`, which makes setup's first destructive step. `guardSourceDatabases()` refuses any app or test name matching any main database name before the worktree is created, and `guardSourceDatabase()` runs again right before the drop. The names (`sourceDatabaseNames()`) are every entry's configured database plus every entry's env keys in the main env file, compared lowercased: an entry is checked against all connections, not just its own, because two can share a server, and MySQL on Windows and macOS ignores case, so `Blog` lands on `blog`. `$cloned` is reset at the start of `handle()` because the console reuses one command instance per process.
- **`worktree:install` is spatie's `hasInstallCommand()`; the GitHub star question is ours** (`WorktreeServiceProvider::askToStar()`, wired through `endWith()`), because spatie's `askToStarRepoOnGitHub()` has fixed generic wording and opens the browser through `exec()`, which a test can't fake. The question names the package and defaults to yes. A run nobody can answer (`--no-interaction`, or no terminal on stdin, as with CI and AI agents) skips the question, takes that default, and prints a star note so the browser tab is explained. `isInteractive()` mirrors Laravel's own prompt rule, including treating unit tests as interactive, which keeps the tests deterministic. The question goes through `$command->confirm()`, never Laravel Prompts' `confirm()`: spatie publishes with `callSilently('vendor:publish')`, and that nested command reconfigures Prompts' global output to a `NullOutput`, so a Prompts question afterwards is invisible while it still waits for Enter. The faked console in tests hides this, so it was only caught in a real terminal. The browser opens through the `Process` facade, so the tests fake it on every OS. Opening is best effort: on Linux, `xdg-open` is backgrounded through `sh`, because without a detected desktop it runs the browser in the foreground, which would hold the command until the browser closed and then trip the 60-second process timeout. Any failure on the interactive path prints the URL instead.
- **Command failures fall back to stdout** (`WorktreeCommand::failure()`) because npm and several Windows tools report errors on stdout with an empty stderr, which produced a bare "Command [x] failed."
- **DatabaseManager connects without a database in the DSN**, so `CREATE DATABASE` works when the target does not exist. Postgres connects to the `postgres` maintenance db, checks `pg_database`, and drops `WITH (FORCE)`. MySQL/MariaDB use `IF NOT EXISTS` / `IF EXISTS`.
- **DB names are lowercased and non-alphanumerics collapse to `_`** (`Worktree::slug()`), keeping them valid on both MySQL and Postgres without quoting headaches.
- **Host remapping uses lookbehind/lookahead** so `blog.test` and the cookie-domain form `.blog.test` are rewritten, but `myblog.test`, `sub.blog.test`, and `blog.testing` are not. The optional leading dot is captured and carried over, which is why `remapHost()` uses a callback rather than a replacement string.
- **Directory::delete() never follows a link, and setup tolerates an empty leftover.** `git worktree remove` leaves behind the `public/storage` link a storage:link step creates, and the surviving directory then blocks setting the branch up again. Laravel's `deleteDirectory()` cannot help: a Windows junction reports `is_link()` false, `is_dir()` false, and `unlink()` fails on it, so `Directory::delete()` spots it by being none of link/dir/file and removes it with `rmdir()`. Windows also keeps a directory handle open for a moment after the contents are gone, so the final `rmdir()` retries with backoff. As a backstop, `createWorktree()` accepts an existing *empty* directory (`Directory::isEmpty()`) instead of only a missing one, because `git worktree add` populates one happily and a stray empty leftover must not block the branch.
- **`git worktree add`/`remove` run with `-c core.longpaths=true`, and teardown finishes a removal git abandoned** (`WorktreeCommand::git()`, `TeardownCommand::removeWorktree()`/`isRegistered()`). Verified on Git for Windows: a worktree whose files pass 260 characters (a deep `vendor`) makes `git worktree remove` fail with "Filename too long" (exit 255), and so does a file another process holds with no sharing ("Invalid argument"). In both cases git has *already unregistered* the worktree, so the old teardown threw with the directory, databases, and branch all left behind. Now, when the remove fails and git no longer lists the path, teardown warns and carries on (`Directory::delete()` handles long paths through PHP); a worktree git still lists was refused on purpose (locked, or dirty without `--force`) and still stops the teardown. Other platforms ignore `core.longpaths`.
- **PhpunitConfig uses DOMDocument**, not regex, so a stock Laravel `phpunit.xml` with commented-out DB lines gets a real `<env>` appended rather than a comment edited.
- **The patched `phpunit.xml` is marked `git update-index --skip-worktree`.** A stock Laravel `phpunit.xml` is tracked and not gitignored, so patching it would leave every worktree permanently dirty: `teardown --into` would refuse to run, and `--pr` would commit the local test database name into the branch. The skip bit lives in that worktree's own index, so it dies with the worktree and never touches the main repo. `ProvisionCommand::prepareTestDatabasesFor()` marks it through `attempt()` rather than `process()`, so a git quirk can never turn the mark into a failed setup.
- **EnvFile is CRLF-aware.** `pattern()` captures the trailing `\r` separately so it never leaks into a value and never gets dropped from a rewritten line. This matters: `WorktreeCommand::isSourceDatabase()` looks the (lowercased) value up among the main database names, and a stray `\r` silently disabled the guard that refuses to drop the main database on Windows. It also recognizes the `export KEY=value` form phpdotenv accepts, both in `keys()` (a key hidden behind `export` would leak into child processes) and in `set()` (the prefix survives a rewrite).
- **Config drives everything** (site driver, worktree path, host template, db naming, migrate mode, steps) so the package fits any project.
- **`node_modules` installs with `npm ci`, not `npm install`, and lives in `dependencies` rather than `steps`.** Laravel's `package.json` has no `name`, so `npm install` writes the worktree's directory name into the tracked `package-lock.json`, dirtying it (and the rename would ride into a commit). `npm ci` installs from the lockfile without rewriting it. Keeping it in `dependencies` (not a step) is what lets the copy optimization skip it. Do not switch it back unless a project has no committed lockfile.
- **`--into` leaves the main repo on the target branch.** Merging requires checking it out, and `git branch -d` needs the merge in `HEAD` to succeed, so teardown does not switch back. In the common case (main repo already on the merge target) nothing moves.
- **Branch arguments are normalized through `cleanBranch()`** (trim whitespace, then strip surrounding quotes). Some terminal launchers substitute a blank text parameter as `''`, and a mis-quoted shell command passes that through as the literal two characters, which used to create a `repo-''` worktree whose quote-laden path then broke `git worktree remove` on Windows. Stripping the quotes turns a blank into an empty string, which auto-generates a branch. `PathCommand` errors on a blank branch rather than resolving `repo-`.
- **`worktree:setup --print-path` prints only the resolved path on stdout**, routing all human output to stderr via `humanOutput()`/`display()` (a stderr-bound `OutputStyle` and a components `Factory` around it). This lets a shell do `cd "$(... --print-path)"` and land in the new worktree, including an auto-generated one. `humanOutput()` builds the stderr style from `$this->output->getOutput()` (falling back to the same stream when it is not a `ConsoleOutputInterface`, as in tests), so `getErrorStyle()` is deliberately avoided (it returns a bare `SymfonyStyle`, which the components `Factory` cannot take).

## Testing

`composer test` runs Pint, PHPStan (level 6, larastan), 100% type coverage, then Pest.

- Pure classes are unit-tested (`WorktreeTest`, `EnvFileTest`, `PhpunitConfigTest`, `DatabaseManagerTest`, `WorktreeListTest`, `DirectoryTest`, `EnumsTest`, `SiteSettingsTest`, `SiteListTest`, `RegistryTest`), and the lock in `FileLockTest`, holding it from a second handle (which conflicts within one process on every OS). `DatabaseClonerTest` clones a fixture holding a foreign key, a generated column, an id-0 row (MySQL), a view on a view, a trigger, a function, and structure-only tables, on both real servers, plus a WAL-mode SQLite file held open so its rows sit in the `-wal` file.
- The server helpers (`serverConnections()`, `serverPdo()`, `serverAvailable()`, `useServer()`, `databaseExists()`, `dropDatabase()`) live in `tests/Pest.php` so every test file can use them; the repo helpers stay in `CommandsTest`. The busy-Postgres clone test skips unless `pg_dump` is at least as new as the server, since pg_dump refuses a newer server.
- `CommandsTest` runs the commands against a **real temporary git repo** created in the system temp dir, mirroring a stock Laravel app: `.env` gitignored, `phpunit.xml` tracked, and a minimal `composer.json` so `composer install` can run. It forces `core.autocrlf false` so a committed lock file keeps identical bytes in the worktree, which the dependency-copy test compares against the source. `site.driver` is `none` throughout and the herd, valet and lerd binaries are names that can't exist, so no test reaches a real server through `auto`, the legacy key, or the Lerd check. A test that needs a server points its binary (or a `command` driver template) at `fakeSiteTool()`, a script that logs each call's arguments and working directory and answers per subcommand (output, exit code, a delay), reached by its absolute path: no PATH edits, so Symfony's Windows executable cache (keyed by bare command name) never comes into it. Driver command sequences are unit-tested against a recording runner (`SiteDriverTest`, which answers per argument string or subcommand, a list answering successive calls), the resolver in `SiteSettingsTest`, and the runner against real processes in `ProcessSiteRunnerTest`. CI configures a global git identity for this (git itself ships on the runner).
- **Every temp repo is deleted, and a repo that can't be deleted fails the test.** `tempRepo()` records each repo in `TempRepos::$created` right after `mkdir`, and `afterEach()` removes all of them (worktrees included), so a repo is cleaned up even when a test's setup throws before its `try`. The `finally { removeRepo() }` blocks stay as early cleanup. `removeRepo()` is best effort and returns what it could not remove, and only `afterEach()` throws, because an exception thrown from a `finally` replaces the test's own failure and Pest's printer never shows the chained one. On Windows `removeRepo()` hands cmd's `rmdir` backslash paths: given `C:\...\Temp/wt-repo-x` it reports `Invalid switch` and deletes nothing, and since `Process::run()` does not throw, that went unnoticed while leftover repos piled up in `%TEMP%`. It retries with backoff for a briefly held handle and uses `rmdir /s /q` rather than `Directory::delete()`, because PHP's `unlink()` cannot remove git's read-only object files. Anything that hands a path to a cmd builtin (`rmdir`, `del`, `mklink`) needs backslashes, and a cleanup step needs a check that it worked. The default SQLite connection's file sits in the testbench skeleton, outside every temp repo, so each setup there gives its worktree a sibling `wt_repo_*.sqlite` file in the skeleton's `database/` directory; `afterEach()` deletes those by that prefix (`TempRepos::$sqliteDirectory`, read in `beforeEach()` before a test repoints the connection), since a test that never tears down used to leave them piling up inside `vendor`.
- **Test repos set `core.fsmonitor false`** right after `git init`, in the repo's shared config so linked worktrees inherit it. With a global `core.fsmonitor=true`, the first index-reading git command in each working tree starts a `git fsmonitor--daemon` that runs until its directory is deleted or the machine restarts, so every leftover repo also kept a process alive.
- **The server-database path runs against real servers rather than mocks.** `useServer($driver)` points the app at MySQL (`127.0.0.1:3306`, root) or Postgres (`127.0.0.1:5432`); the driver-specific tests are parameterized `->with(['mysql', 'pgsql'])` and `->skip()` when no server answers, so the suite still passes on a machine without one. CI runs both a mysql and a postgres service.
- Adopt tests make the tool's worktree with raw `git worktree add` at `<repo>-<suffix>` (`toolWorktree()`), where `removeRepo()` finds it. The shim test runs the shipped stub from a subdirectory of the worktree against a stand-in `artisan` in the main checkout that records its arguments, cwd and `display_errors`.
- The env-leak test guards the worst bug this package had. It sets `WT_LEAK_CHECK` through putenv **and** `$_ENV`/`$_SERVER`, because Symfony only forwards variables present in `$_SERVER`: using putenv alone makes the test pass whether the fix is there or not.
- Tests use `WithWorkbench` + `testbench.yaml`.

## Development notes

- **Depends on split `illuminate/*` components (console, contracts, filesystem, process, support), not `laravel/framework`.** GitHub security advisories for Laravel are scoped to the `laravel/framework` package, so requiring the individual components keeps this repo off those advisories while still supporting Laravel 12/13 (the framework `replace`s every component, so it resolves fine in a real app and in testbench). This is why the source uses `$this->laravel->basePath()`, the `Config` facade, and `Illuminate\Support\Carbon` rather than the `base_path()`, `config()`, and `now()` foundation helpers, which are only defined when `laravel/framework` is present. Do not reintroduce those helpers or add `laravel/framework` to `require`.
- The commands run real processes through the `Process` facade. Structured calls (git, site drivers, php artisan) use array commands; user-configured `steps` are strings run through the shell so flags like `--if-present` work.
- `larastan.noEnvCallsOutsideOfConfig` is ignored for `config/worktree.php` in `phpstan.neon.dist` (env() in a config file is correct).
- Target is PHP 8.2+, Laravel 12/13. Keep source 8.2-safe: no unwrapped `new Foo()->bar()` chaining, no typed class constants. Pest is constrained to `^3.8.2|^4.0.0|^5.0.0` because Pest 4 requires PHP 8.3, and pinning it to `^4.0` alone would drag the whole package's floor up to 8.3.
- No facade, no migrations, no views. Do not add a `down()` to any migration (there are none), and follow these conventions: protected over private, guard clauses over else, explicit types.
